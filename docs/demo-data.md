Все сведения вымышлены. scripts/demo-data.ts создаёт один воспроизводимый
набор для серверного seed и локальной проверки интерфейса. Приложение
продолжает читать данные через portalApi; этот генератор не входит в браузерную
сборку и не подменяет Supabase в продукте.

## Успеваемость

Счётчик «Долги за период» и переключатель «Только долги» используют только
опубликованные результаты «2», «Не зачтено» и их текстовые варианты.
Выбор семестра пересчитывает счётчик и список. В среднем балле учитываются
только числа 2–5; зачёты не превращаются в нули. Пустой отфильтрованный список
объясняет, что долгов за выбранный период нет.

Это представление отрицательных результатов за период. Отдельного реестра
закрытия задолженностей в контракте API пока нет; старые отрицательные оценки
не выдаются за сведения из такого реестра.

## Первичное заполнение выделенного Supabase

Использовать только отдельный демо-проект с двумя вымышленными аккаунтами.
Нужны существующие локальные SUPABASE_URL, SUPABASE_SECRET_KEY и явный
PORTAL_ALLOW_DEMO_SEED=yes в ignored .env. В браузер попадает только
публикуемый ключ; административный ключ и пароли не публикуются.

В пустом демо-проекте: npm run seed:demo. Скрипт создаёт аккаунты и случайные
пароли, сохраняя их только в ignored work/demo-credentials.json. Его нельзя
перезапускать вслепую поверх существующих пользователей.

## Обновление уже созданных демо-аккаунтов

```sh
node --env-file=.env --experimental-strip-types scripts/refresh-demo.ts
```

Скрипт заранее находит оба известных email и проверяет наличие обоих профилей.
Если одного нет, запись не начинается. Затем обновляет только строки
генератора по стабильным ID: расписание и результаты обновляются, история
заявок и отметки о прочтении сохраняются. Пароли, Auth settings и профили
не меняются. Чужие и прежние строки не удаляются. После частичного сбоя этот
скрипт можно повторить: данные не дублируются. Обновление повторяют перед
показом, чтобы расписание относилось к текущей неделе.

Триггеры Supabase могут добавить служебные уведомления при первичном создании
примеров заявок. Ручная обработка заявок из этого не следует.

04.11.2026 по разрешению пользователя владелец #4 выполнил обновление
в выделенном проекте student-portal-hackathon и повторил его для проверки
идемпотентности. Дубли не появились; прежние записи, профили, статусы и
прочтение сохранились. Старые два занятия и две оценки не удалялись:
в облаке теперь по 15 занятий и 10 результатов на студента, включая
14 новых занятий и 9 новых результатов. Это отличается от чистого набора
в таблице выше сохранёнными строками первоначального seed.

После обновления прошли 55 Auth/REST и 17 целевых браузерных проверок
с настоящими аккаунтами. [Отчёт и снимки](redesign-acceptance.md).

## Проверки

Полный запуск:

```sh
npm run check
npm test
npm run build
```

В текущей ветке дополнения R5 обычный npm test включает 31 тест.
Генератор проверен
на распределение пар по неделе, раздельные ID студентов, даты, типы результатов
и повторяемость ID. refresh-demo.ts дважды выполнен против изолированного
HTTP-стенда с настоящим SDK: нет дублей, не сбрасываются статусы и прочтение,
при отсутствии профиля запись запрещена. Это не тест реальной облачной RLS.

состояние, разные данные A/B, примеры статусов, новая заявка и уведомление,
прочтение, 360 px и длительность перехода 280 мс. Наблюдаемых JS-ошибок нет.
Настройка reduced-motion по-прежнему отключает движение.

## Напоминание с конкретным сроком

Генератор добавляет по одному вымышленному уведомлению A/B с дедлайном
через три московских календарных дня, временем 18:00 МСК и действием:
заявление о теме проекта для A, о месте практики для B. Текст прямо говорит,
что это учебный пример. Используется существующий Notification title/body;
схема, SDK и UI не меняются. Это не планировщик и не автоматическая рассылка.

В выделенном демо после отдельного разрешения можно применить только эти
уведомления, без обновления расписания, оценок, заявок или счетов:

```sh
node --env-file=.env --experimental-strip-types scripts/refresh-demo.ts --reminders-only
```

Оба пользователя и профиля проверяются до первой записи. ID зависит от
владельца и даты срока: повтор того же срока не создаёт дубль и сохраняет
прочтение. В другой московский день создаётся новый вымышленный срок с новым
ID; старые уведомления не перезаписываются. Не запускать ежедневно без
необходимости. Пароли, Auth settings и остальные строки не меняются.

Тесты проверяют дату на границе московской полуночи и года, различие A/B,
повторяемость ID, отдельный режим только notifications, отсутствие дублей,
сохранение прочтения и запрет записи при неполном preflight/неизвестном флаге.
Первоначальная локальная подготовка не выдавалась за облачную приёмку.
Облачный прогон по отдельному разрешению описан ниже.

Локальный интерфейс с реальным React/SDK и HTTP-фикстурой прошёл три
проверки: отдельное уведомление, явный срок/действие/маркировка и отсутствие
переполнения при 360 px. [Протокол](reminders/local-browser.json) и
[снимок](reminders/local-mobile.png). Это локальный прогон; отдельная облачная проверка приведена ниже.
